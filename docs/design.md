# rulefit 设计说明

这份文档记录"为什么这样做"，README 记录"怎么用"。判断依据全部可以用一句话检验：
**一个判断要么被构造出来的具体路径证明，要么被明确标成 `[unproven]`，不允许出现第三种状态。**

## 一、问题从哪来

代码评审类工具（静态分析、lint 机器人、AI review）的配置基本都由两半组成：

1. **白名单**：愿意看的文件类型；
2. **路径 → 规则 的映射**：一串 glob 到领域规则文档的对应表。

这两半都会持续膨胀。以 `alibaba/open-code-review` 为例：115 个扩展名、55 条路径规则、50+ 份规则文档。膨胀之后出现的问题不是"代码写错了"，而是**配置之间互相不认账**：

| 现象 | 真实后果 |
| --- | --- |
| 两个模式都能匹配同一类文件 | 谁生效取决于 map 里的书写顺序，重排一次顺序就静默改变行为 |
| 规则文档写了，但没有任何扩展名能走到它 | 规则形同不存在，而且没人会发现 |
| 模式匹配不到任何白名单文件类型 | 同上，只是更隐蔽 |
| 扩展名在白名单里但没有任何规则路由它 | 永远落到 default，评审质量退化 |
| 花括号写法不被解析器支持 | 模式含义与作者以为的不一样，且不报错 |

这些问题的共同点是：**它们不会让程序崩溃，只会让评审悄悄失效**。所以需要一个能进 CI、只看配置文件就给出确定结论的检查器。

## 二、定位与不做的事

**做**：一个配置一致性检查器。输入是配置，不扫描仓库，输出是确定性的报告。

不做，且明确写进 README 的"Scope and non-goals"：

- 不检查"这个规则本身写得好不好"；
- 不检查模式是否匹配**当前仓库里真实存在的文件**（那需要扫仓库，且和"白名单允许"是两件事）；
- 不支持任意 glob 方言（只支持明确列出的一张表）；
- 不自动修配置（第一版只诊断，避免制造新的静默行为）。

## 三、架构

```
cmd/rulefit            CLI：check / explain 两个子命令，退出码 0/1/2
internal/config        读审计配置 + 用 selector 取出两半数据（保留声明顺序）
internal/glob          glob 方言：解析、匹配、重叠判定（无第三方依赖）
internal/check         六类检查，产出结构化 Finding
internal/report        text / json / sarif 三种渲染
```

关键取舍：

- **零第三方依赖**。glob 引擎自己实现。理由是工具的长期价值在于"任何环境都能跑"，而它的核心算法本来就是这个项目最想展示的部分。
- **配置驱动，不硬编码某个项目**。`config.Spec` 用点号 selector 描述"数据在哪个文件的哪个键下面"，所以同一份二进制能审任何"白名单 + 路径规则"形态的工具。
- **读原始字节，不重新编码**。`selectNode` 返回 `json.RawMessage` 而非 `map[string]any`：路径映射的**声明顺序就是行为**，一旦经过 Go map 再编码回来，顺序就丢了。（这个坑在开发中真实踩到过，`TestLoadKeepsDeclarationOrder` 就是它的回归测试。）

## 四、核心算法：怎么判断"两个模式是否竞争"

这是全项目唯一有技术难度的地方，也是 `OpenCodeReview` 上游审计脚本里两个临时程序（`verify-language-coverage`、`pattern-collisions`）各自只做了一半的地方。

### 4.1 为什么不能用"试探法"

最省事的做法是拿一堆探针路径去试。但探针永远不完备：`**/pom.xml` 对 `**/*.xml` 是重叠的，而 `**/pom.xml` 对 `**/*.yaml` 不是；`**/*.properties` 对 `**/*.xml` 不是；`*.xml` 对 `*mapper*.xml` 又是。用"最后一个 literal 后缀不同 → 不相交"这种规则去判断，`**/*.xml` 对 `**/*{Mapper,Dao}*.xml` 就会判错（两者其实重叠）。

所以判定必须是**构造性的**，而不是启发式的。

### 4.2 两层构造

**第一层：段级（`**`）** —— `segmentsOverlap` 是两条"类 NFA"的乘积构造：

- `**` 是自发转移（可匹配零个段、可持续吞段）；
- 具体段必须被"对账"：要么逐字符匹配，要么被对方 `**` 整段吸收；
- 结尾只剩 `**` 才算对账成功（`convergenceTail`）。

结论偏保守：**只有在能证伪时才判不相交**，证不出来就报告重叠（在报告里体现为 warning 或 `[unproven]`）。这个方向是刻意的——漏报一个真实的规则遮蔽，比多报一条需要人工确认的 warning 严重得多。

**第二层：字符级（段内）** —— `segmentsIntersect` 在元素序列上做乘积：

- 状态 `(i, j)`，`*` 是唯一的分支点（吞一个元素 / 不吞）；
- 两个具体元素必须 `elementsCompatible`（literal 与 class 用 `matchesByte` 求交）；
- 不同的扩展名在 `.p…` 处就对不上，因此 `**/*.properties` 与 `**/*.xml` 判为不相交。

### 4.3 见证路径（witness）

判定为重叠之后，还要给出**证据**：一个同时匹配两个模式、且在允许范围内的具体路径。

做法不是"直接算出交集语言"，而是**生成候选 + 逐个验证**：

1. 把每个模式各自的 alternate 渲染成 glob（`remainingSegments`）；
2. 实例化：`*` → `""` 或 `"x"`，`?` → `"a"`，`**` → 空或一层目录；
3. 用**真正的匹配器**验证候选是否同时匹配两个原始模式；
4. 用白名单谓词（`extensionAcceptor`）验证它确实是工具会处理的文件。

所以报告里的每一行 `witness:` 都是被匹配器验证过的路径，不是推出来的。

### 4.4 遮蔽方向（kind）

证据只说明"重叠"，方向还需要单独测：

- 从 A 的所有可接受路径里取样本，若**全部**被 B 匹配 → A 被 B 包含 → A 在前，B 的规则**永远不会被选中**（`a-shadows-b`）；
- 反向成立 → `b-shadows-a`（B 更宽，A 仍在自己那部分路径上胜出）；
- 都不成立 → `partial`（谁赢取决于具体路径）。

这个结论是可操作的：`a-shadows-b` 意味着"要么挪走 B，要么把 B 放到 A 前面"。

### 4.5 退出码与"严格模式"

唯一无法替用户决定的问题是：**扩展名落到 default 规则算不算缺陷？** 有兜底规则的工具里这是合法的，没有的则是缺陷。所以它由 `--strict` 决定，默认只作为 note 报告。

## 五、验证方式

项目不依赖 golden 字符串，而是把行为写成**性质（property）**：

| 测试 | 保证的性质 |
| --- | --- |
| `TestSegmentsOverlapAgreesWithMatching` | 暴力枚举短路径：只要存在一条路径同时匹配两个模式，`SegmentsOverlap` 必须返回 true（防漏报） |
| `TestFindOverlap` | 每个 exact 结论都带 witness，且 witness 必须被两个模式匹配 |
| `TestFindOverlapUnknownWhenNoWitness` | 造不出路径时必须 `ConfidenceUnknown`，不得冒充 exact |
| `TestLoadKeepsDeclarationOrder` | 声明顺序不得丢失 |
| 各 `TestRun*` | 六类检查各自的触发与忽略（ignore 列表 / ignore 模式）行为 |

开发过程中这些性质测试真的抓到了四个 bug：星号匹配的记忆化键冲突、`**` 与 `*` 的语义混淆、字面量锚点自证（`**/*.kt` 因为探针里出现 `.kt` 而看起来"活着"）、以及 `**` 段级构造的方向错误。诚实地说，这个模块的正确性来自"性质测试 + 保守回退"，而不是来自一次写对。

## 六、第一次跑真实配置（上游 main，2026-10-07）

把这套东西指向一份**不是为它写的**配置，结果比单元测试更有价值：查出上游 1 个真实不一致，同时查出**工具自己 3 个 bug**。完整证据见
[`docs/findings/opencodereview-2026-10.md`](findings/opencodereview-2026-10.md)，这里只留结论。

**上游的真实发现（1 条）**：`system_rules.json` 第 37 行写 `"**/*.R": "r.md"`，而白名单里只有小写 `".r"`、没有 `".R"`。该工具在匹配前会把模式和路径都转小写，所以这个规则"实际能用"，但它与对应的白名单条目对不上——`rulefit` 报告这个不一致，由人来决定改模式还是改白名单。另有 37/115 个扩展名没有语言规则、落到 `default.md`（属于产品决策，所以只是 note）。

**工具自己的 3 个 bug**：

| # | 症状 | 根因 | 现在由谁守住 |
| --- | --- | --- | --- |
| 1 | `**/pom.xml`、`**/package.json` 这类整文件名规则全被报成 dead-pattern | 探针只从白名单派生，没从模式自身的字面量派生 | `TestRunKeepsWholeFileNameRulesAlive`、`TestRunReportsExtensionNotInAllowlist` |
| 2 | 报的行号偏小（说第 34 行，实际第 37 行） | 行号由"在选中子树里排第几"推算，而 JSON 里 `path_rule_map` 前面还有 3 行 | `TestRunReportsSourceLines`、`TestLoadKeepsDeclarationOrder` |
| 3 | 5 条 shadowed-rule 误报，方向还说反了 | 只测出"重叠"，把"具体规则在前、通用兜底在后"这种健康写法也报了 | `TestRunFlagsTheGeneralBeforeSpecificOrdering`、`TestRunKeepsWholeFileNameRulesAlive` |

第 3 个是**语义**问题而不是代码 bug。第一版只在报告里写"两个模式竞争"，没有区分方向；而对一个 first-match-wins 的映射，唯一值得报警的方向是"**前面的模式已经覆盖了后面模式的所有路径**"，也就是后面的规则永远选不中。反过来（前面更窄、后面是兜底）恰恰是正确写法。

修法不是改文案，而是把方向编进**类型名**：

| Kind | 含义 | 是否报告 |
| --- | --- | --- |
| `earlier-unreachable` | 前面的模式更窄，后面的模式是它的兜底 | 不报 |
| `later-unreachable` | 前面的模式已覆盖后面模式的全部路径，后面的规则永不生效 | 报告（warning） |
| `partial` | 两者共享部分路径，谁赢取决于具体路径 | 报告（warning） |

旧命名是 `a-shadows-b` / `b-shadows-a`——这次开发里我**把它读反了两次**，多花了两轮调试。改名之后，这类错误在代码审查阶段就能看出来，而不是靠跑测试才发现。

顺带修掉两处相关的正确性问题：

- **包含关系不能在白名单过滤之后再测**。两侧都被过滤成同一批"可接受路径"时，更宽的模式看起来和更窄的一样宽，方向就判反。现在先用未过滤候选集判定包含关系，再用白名单谓词判定"这条路径工具真的会处理"，两件事分开。
- **`\n` 与 `\r\n` 都要算换行**。Windows 检出是 CRLF、从 Git 对象读出来是 LF，同一份配置必须报同一个行号。

## 七、路线图

1. **更多适配器**：为 `.yaml` 配置的 linter、白名单内联在其他文件里的工具各加一个 `examples/` fixture。
2. **`--baseline`**：接受今天的基线，只对新增问题失败。这是大配置能落地的前提。
3. **`--fix`（谨慎）**：只做无损重排（把具体规则提到宽泛规则之前），且必须带 `--dry-run`。
4. **GitHub Action**：把报告作为 PR 评论贴出，并上传 SARIF 供 code scanning 标注。
5. **段内 `**` 语义**：目前 `*` 不跨段，这与 doublestar 一致，但有些工具把 `**` 写在段内，需要按项目开关。

## 八、开发日志（可复核）

- 语言/工具链：Go 1.27.1（便携版，全部在 E 盘），零第三方依赖。
- 测试：`go test ./... -cover`，当前覆盖率 check 82.9%、config 84.2%、report 93.1%、cmd 70.6%、glob 64.4%。
- 提交前的固定动作：`gofmt -l .`（必须为空）+ `go vet ./...` + `go test ./...` + 对 `testdata/fixture-repo` 与 `testdata/fixture-defects` 各跑一次 `rulefit check`（CI 同款）。
- 两个 fixture 的分工：`fixture-repo` 是**健康**配置（CI 用它证明工具不误报），`fixture-defects` 是一个**故意有病**的配置（三类发现各一条，用来证明工具真的会报）。
